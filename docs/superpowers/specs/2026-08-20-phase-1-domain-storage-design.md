# FideliChem Phase 1 Domain and Storage Design

## Status and source of truth

This specification narrows Phase 1 of `FideliChem_PLANO_CODEX.md` into a
storage foundation. The product plan remains authoritative for later scientific
entities and behavior. Phase 1 establishes a versioned project database,
immutable provenance records, transactional repositories, and an append-only
audit trail.

## Goal

Create a portable SQLite-backed storage layer that can create and reopen a
FideliChem project, preserve imported-file provenance exactly, record relevant
changes atomically, and reverse an import batch without deleting its raw
evidence or history.

## Scope boundary

Phase 1 includes four public immutable domain entities:

- `Project`;
- `ImportBatch`;
- `SourceArtifact`;
- `AuditEvent`.

It also includes project-directory creation, SQLAlchemy 2.x ORM mappings,
repositories, transaction framing, the first Alembic migration, database-level
immutability enforcement, hashing/JSON utilities, and migration/integrity
checks.

The following are deliberately deferred:

- `Compound`, `MolecularState`, and `Alias`, whose identity semantics belong to
  Phase 2;
- adapters and import orchestration, which belong to Phases 3 and 4;
- targets, docking runs, poses, score definitions, and score observations,
  whose real constraints depend on later adapter and score phases;
- interactions, molecular-dynamics data, analytics, decisions, and GUI flows;
- physical copying for the future `Make project portable` command.

Deferring those tables is preferable to freezing constraints before their
scientific behavior is specified. Alembic provides the controlled expansion
path.

## Chosen architecture

Use a strict separation between immutable Pydantic domain values and private
mutable SQLAlchemy persistence rows:

```text
application/service
        |
        v
frozen domain models
        |
        v
repositories + transaction manager
        |
        v
SQLAlchemy ORM + SQLite + Alembic
```

Repositories accept a caller-owned SQLAlchemy `Session`. A transaction manager
owns `Session.begin()` boundaries; repositories never commit independently.
This allows a domain mutation and its audit event to succeed or roll back as a
single unit. No global session is shared across threads.

Runtime dependencies added in this phase are Pydantic 2.x, SQLAlchemy 2.x, and
Alembic 1.x. The lockfile selects exact versions.

## Domain contracts

All public domain models use `ConfigDict(frozen=True, extra="forbid")`. IDs are
opaque UUID4 strings generated by the application. They are stable across
database reopen and are never derived from a filename, rowid, or external ID.
All timestamps are timezone-aware UTC values.

### Project

`Project` contains `id`, `name`, optional `description`, `created_at`,
`updated_at`, and `schema_version`. A database contains one project record.
Names must be non-blank. Schema version records the project-model version; the
Alembic revision remains the database-schema source of truth.

### ImportBatch

`ImportBatch` contains the fields from the product plan plus `project_id`,
`rolled_back_at`, and an optional rollback reason. Status is a closed enum:
`in_progress`, `completed`, `failed`, or `rolled_back`.

Allowed transitions are:

```text
in_progress -> completed
in_progress -> failed
completed   -> rolled_back
failed      -> rolled_back
rolled_back -> rolled_back  (idempotent no-op)
```

Adapter identity, source root, input hash, start time, warnings, and file count
are immutable once inserted. Completion and rollback metadata may only change
through the lifecycle repository.

### SourceArtifact

`SourceArtifact` contains `id`, `import_batch_id`, original `path`, normalized
POSIX-style `relative_path`, lowercase SHA-256, file type, non-negative size,
and timezone-aware modification time. The original path is provenance metadata,
not an identity or a path that the application executes.

Artifacts are append-only. `UPDATE`, `DELETE`, and replacement semantics are
rejected by SQLite triggers. A rollback preserves artifacts and marks their
batch inactive. SHA-256 validation occurs at the domain boundary and database
constraints preserve the normalized representation.

### AuditEvent

`AuditEvent` contains a stable ID and database-generated ordering sequence, UTC
timestamp, action, entity type and ID, optional import-batch correlation,
canonical JSON strings for old/new values, source, actor kind (`user` or
`system`), and optional actor ID.

Audit rows are append-only through database triggers. `import_batch_id` is a
nullable foreign key with `ON DELETE RESTRICT`, because batches are permanent;
other entity correlations remain scalar IDs so history can survive future
entity removal. The ordering sequence is strictly increasing across committed
rows, is not promised to be contiguous, and is never treated as a domain ID;
sequence values from rolled-back rows are not observable. Canonical JSON sorts
keys, rejects NaN/Infinity, and preserves the distinction between null, zero,
false, and empty text.

## Relational schema and delete policy

Tables use singular snake-case names and named constraints/indexes:

- `project`: UUID text primary key and one-row guard;
- `import_batch`: UUID text primary key, `project_id` foreign key with
  `ON DELETE RESTRICT`, status checks, and adapter/input-hash indexes;
- `source_artifact`: UUID text primary key, `import_batch_id` foreign key with
  `ON DELETE RESTRICT`, unique `(import_batch_id, relative_path)`, and SHA/size
  checks;
- `audit_event`: UUID text primary key, integer ordering sequence, optional
  `import_batch_id` foreign key with `ON DELETE RESTRICT`, and query indexes.

There is no broad `ON DELETE CASCADE`. Project, batches, raw artifacts, and
audit events are not physically deleted by the public repositories. This makes
rollback reversible without destroying provenance. Later phases must associate
imported evidence with a batch and treat a rolled-back batch as withdrawn.

## SQLite engine and transactions

Every engine created by FideliChem registers a connection hook that executes
`PRAGMA foreign_keys=ON` before any transaction or schema creation. File-backed
databases use an explicit absolute path and never infer one from the current
working directory. Read-only access uses SQLite URI `mode=ro&uri=true`;
`immutable=1` is not used for a live project.

Write operations run inside a context-managed unit of work. A failed flush,
constraint, hash check, lifecycle transition, or audit insert rolls back the
entire operation. Public errors are domain-specific and do not expose raw SQL.

## Project layout

Creating a project root produces:

```text
MyProject/
├── project.fidelichem.sqlite
├── project.json
├── artifacts/
├── cache/
├── exports/
└── logs/
```

Creation fails if the target contains a conflicting project instead of
overwriting it. `project.json` is UTF-8 canonical JSON containing the project
ID, display name, schema version, and relative database filename. Paths stored
in it are relative and validated against traversal. Project creation applies
the Alembic head before inserting the project record; partial creation is
cleaned up only when all targets are confirmed to belong to the failed new
project operation.

## Migrations

Alembic lives inside the installed `fidelichem.storage.migrations` package.
Programmatic configuration supplies the migration location and an existing
SQLAlchemy connection. The initial revision creates all four tables, indexes,
constraints, and immutability triggers.

Public migration helpers:

- upgrade a database to `head`;
- obtain current and head revisions;
- assert that a database is at the supported head;
- reject a database stamped with an unknown/future revision without modifying
  it.

Migration tests use real temporary files, reopen them, run SQLite
`integrity_check` and `foreign_key_check`, and verify repeated upgrade is safe.
Future schema changes must use Alembic batch operations when SQLite cannot
perform the requested alteration directly.

## Repository contracts

- `ProjectRepository`: add, get, and update project metadata with audit in the
  same transaction.
- `ImportBatchRepository`: add, get, complete, fail, and logically roll back a
  batch; invalid transitions raise a domain error.
- `SourceArtifactRepository`: add, get, and list by batch; no update/delete API.
- `AuditRepository`: append and list events; no update/delete API.

All reads return fresh frozen domain values, not ORM rows. Missing records
return `None`; invalid writes raise typed errors. A batch rollback is
idempotent, preserves all source artifacts, and appends exactly one rollback
audit event.

## Test strategy

Strict RED-GREEN-REFACTOR covers:

- frozen model validation, UUID stability, UTC timestamps, SHA-256, and
  canonical JSON;
- project layout and safe conflict/path handling;
- initial migration, repeated upgrade, unknown revision refusal, integrity,
  and database reopen;
- foreign keys enabled on every connection and invalid parent rejection;
- create/read round trips through repositories;
- atomic rollback after intermediate failure;
- database-level rejection of artifact/audit update and delete;
- legal and illegal batch transitions;
- idempotent logical rollback preserving hashes/artifacts and audit history;
- explicit preservation of `None` versus zero/false/empty string.

The complete repository must retain at least 80% branch coverage, and the new
domain/storage modules must independently meet that threshold.

## Security and robustness

- SQL is emitted through SQLAlchemy or fixed migration statements; no user
  value is interpolated into SQL.
- Imported paths are stored as inert metadata and never executed.
- Relative paths reject absolute paths, drive prefixes, `..`, and NUL bytes.
- JSON rejects non-finite numbers and unsupported values.
- No pickle, `eval`, secrets, telemetry, network service, or scientific
  executable is introduced.
- Large scientific coordinates and input contents remain outside SQLite.

## Acceptance gate

Phase 1 is accepted only when:

- a project can be created, closed, and reopened with the same ID;
- every application connection reports `PRAGMA foreign_keys=1`;
- migration to head is repeatable and integrity checks are clean;
- repository writes are atomic and foreign-key violations roll back;
- raw artifacts and audit events cannot be changed or deleted, including via
  direct SQL;
- batch rollback is idempotent and preserves source provenance;
- the full suite, branch coverage, Ruff, mypy, lock check, dependency audit,
  build, installed-dependency check, and diff check pass;
- a Terra xhigh review has no unresolved critical or important findings.
